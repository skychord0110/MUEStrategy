# edinet_holder_monitor — 大量保有報告書モニタ（大口の売り切りタイミング検知）

EDINET API v2 でウォッチリスト銘柄の**大量保有報告書・変更報告書**を毎日チェックし、
大口保有者の売却進捗を追跡する。報告書に記載された**残りの保有株数**を起点に、
その後の**平常時を超えた出来高でこなされた**と仮定して消化状況を推定し、
**保有株がなくなるタイミング（＝売り圧力の解消＝需給改善）で通知**する。

検知・通知のみで**発注は行わない**。kabuランナーとは独立した1日1回実行のバッチツール。

## なぜこれが効くのか

大口保有者（ファンド等）が持ち株を売り続けている間、株価は上値を抑えられ続ける。
その売りが終わった瞬間に需給が一気に改善し、上昇に転じることがある。
変更報告書は**保有割合が段階的に下がる様子を開示する**（例: 8%→7%→6%→5.1%）ため、
「あと少しで売り切る」が**事前に**見える。5%を割ると報告義務が消滅し、これが確定シグナルになる。

### 実例での検証（クルーズ 2138）

2138は5/25の508円から7/2の361円まで約5週間下落し、7/3を境に上昇に転じた（7/17に465円）。
本ツールの消化モデルに「6/20時点で50万株の残存保有」を与えて計算すると:

```
平常出来高(中央値) 19,200株
2026-07-02 累計消化   404,700株
2026-07-03 出来高 551,000（超過 531,800）→ 累計 936,500株  ← 50万株を突破
```

**消化完了の推定日は2026-07-03** となり、実際に上昇が始まった日と一致した。
7/3単日で超過出来高53万株（平常の約28日分）が出ており、最後の売り玉がまとめて
消化されたことが数値に表れている。

## 検知・通知の種類

| 通知 | 条件 | 意味 |
|---|---|---|
| `比率低下` | 変更報告書で保有割合が前回より低下 | 売却が進行中 |
| `5%接近` | 保有割合が6%未満（設定可）5%以上 | 報告義務消滅が近い＝売り切りが近い |
| `5%割れ` | 保有割合が5%未満（報告義務消滅） | **売却完了が確定的** |
| `消化50% / 80%` | 超過出来高の累計が残存株数のN%に到達 | 売り切りが近づいている |
| **`売り切り推定`** | 累計超過出来高 ≧ 残存保有株数 | **保有株が消化され尽くした推定＝メインシグナル** |
| `売り切り接近` | 直近ペースで残りN営業日以内（既定5日） | 事前アラート |

## 消化モデル

```
その日の消化量 = max(0, 出来高 − 平常出来高) × 重み × seller_share
消化率 = 累計消化量 ÷ 報告書時点の保有株券等の数
```

- **平常出来高**: 報告日以前180日の出来高の**中央値**（急増日に引きずられない）
- **seller_share**: 超過出来高のうち当該保有者に帰属すると仮定する割合（既定1.0）。
  1.0は消化を早めに見積もるので、慎重に見るなら0.5〜0.8に下げる
- **split_among_holders**（既定true）: 同一銘柄に売り手が複数いる場合、超過出来高を
  人数で按分する。各自に丸ごと割り当てると二重計上になり消化を大幅に過大評価するため
  （例: 4813は清原達郎・古川良太・SBI証券の3名が同時に売却中）
- **max_report_age_days**（既定90）: 報告日がこれより古い保有者は計算対象外。
  訂正報告書は数ヶ月前の報告義務発生日を持つことがあり、その間の出来高を全部積算すると
  消化率が数百%という無意味な値になるため
- **down_day_weight / up_day_weight**: 下落日・上昇日の重み（既定はどちらも1.0＝区別しない）。
  下落局面でこなされているという見立てを強めるなら up_day_weight を下げる
- **売り切り見込み日数**: 直近10営業日の平均消化ペースから残り営業日を逆算

## セットアップ

### 1. EDINET APIキーの取得（必須）

EDINET API v2 は**APIキー（Subscription-Key）が必須**。EDINETのサイトで無償登録して取得する。
未設定だと `401 Access denied due to invalid subscription key` が返る。

```powershell
# そのセッションだけ有効
$env:EDINET_API_KEY = "取得したAPIキー"

# 永続化する場合（新しいターミナルから有効。以後の設定は不要）
setx EDINET_API_KEY "取得したAPIキー"
```

**APIキーはこのファイルやconfigに書かないこと。** git管理下のファイルに書くと
commit/pushで外部に漏れる。環境変数だけで渡す運用にする。

### 2. 実行

```powershell
cd strategies\edinet_holder_monitor
pip install -r requirements.txt
cd src
python main.py --config ../config.yaml
```

1日1回（引け後）の実行を想定。状態は `state/holders.json` に永続化され、
同じ通知は二度出ない。ログは `logs/edinet_holder_YYYY-MM-DD.log` に日付別で保存。

**初回は遡ってチェックする**とよい（既定は7日）:

```powershell
python main.py --config ../config.yaml --days 60
```

### 3. 初回の項目名確認（推奨）

XBRLの項目名は改訂で変わり得るため、抽出できているか最初に確認する:

```powershell
python main.py --config ../config.yaml --days 30 --debug-dump
```

該当書類の「要素ID / 項目名 / 値」が一覧表示される。
`保有株券等の数` `株券等保有割合` が想定と違う名前なら
`src/edinet_client.py` の `extract_holding()` を調整する。

## 設定（config.yaml）

- `edinet.*`: 遡り日数・API間隔・書類種別コード・書類名キーワード
- `absorption.*`: 消化モデルのパラメータ（平常出来高の期間・seller_share・重み）
- `notify.*`: 通知のしきい値（消化率・5%接近ライン・ETA日数）

## 重要な前提・限界

- **消化モデルはヒューリスティック**。超過出来高が本当にその保有者の売りかは検証できず、
  他の売り手・買い需要も混在する。「売り切り推定」は**目安であり確定情報ではない**。
  確定シグナルは「5%割れの変更報告書（報告義務消滅）」の方
- **同一銘柄に複数の売り手がいると精度が落ちる**。`split_among_holders` で人数按分するが、
  実際の売却ペースは保有者ごとに異なるため、あくまで粗い近似
- 大量保有報告書の**提出者は保有者（ファンド・個人）**であり、メタデータの `secCode` は
  基本 null。銘柄の特定は `issuerEdinetCode` → EDINETコードリストで証券コードに変換して行う
  （対応表は `state/edinet_codes.json` に7日間キャッシュ）
- XBRLの**保有割合は小数**で入る（`0.1330` = 13.30%）。本ツールは%に換算して扱う
- **提出期限は5営業日**あるため、報告書の内容は最大5営業日前の状態。ただし比率が
  段階的に下がる様子から先読みできるのが本ツールの狙い
- 保有割合が最初から5%未満の売り手、5%未満に分散して保有する売り手は捕捉できない
  （そもそも報告義務がないため）
- 日足はYahoo Financeから取得している（`analysis/` と同じ方式）
- 書類種別コード（350/360）は環境差の可能性があるため、書類名キーワードでも
  判定する二重の絞り込みにしている。取りこぼす場合は `config.yaml` の
  `edinet.doc_type_codes` / `edinet.keywords` を調整する

## 関連

- 値動きから同種の事象を当日リアルタイムに捉える案（出来高急増＋長期下落からの反転）は、
  バックテストでは勝率がベースラインを下回る高分散シグナルだった。本ツール（因果が明確）と
  組み合わせて確度を上げる使い方を想定している
