# periodic_buy_rss — 歩み値による定期買い集め検知

**ある約定の丁度10秒後に買いが入る**動きが1日に何度も（既定5回以上）繰り返されている
ときに通知する。光通信のような事業会社が買い集めているサインの疑い。

検知・通知のみで**発注は行わない**。統合ランナーから自動起動される。

## 取得元は2通り（config の `source`）

| | **kabu（既定・推奨）** | rss（旧方式） |
|---|---|---|
| API | kabuステーション `/timeandsales` | 楽天MS2 RSS `RssTickList`（Excel経由） |
| 取得件数 | **上限なし**（4889で5,911件） | 直近**300件**まで |
| 時刻 | **ISO8601・日付/TZ付き** | `15:24:25`（日付なし） |
| 銘柄登録 | **不要** | 必要 |
| 必要なもの | なし | Excel＋マーケットスピードII＋COM |
| 制約 | レート制限（429） | Excelのビジー・COM不安定 |

**2026-08-10に実機で確認して kabu を既定にした。** RSSの2大弱点——「300件上限」と
「日付が無く前営業日のティックを当日と誤認する」——が構造的に解消される。

レート制限はあるが**毎回その日の全件が返る**ため、間隔を空けても取りこぼしは起きず
検知が遅れるだけ。50銘柄を1秒間隔で回して1周およそ50秒。

ディレクトリ名の `_rss` は旧方式の名残（RSS経路も `source: "rss"` で使える）。

## 仕組み

1. 歩み値（**時刻・出来高・約定値**）を取得する
   - kabu: `GET /timeandsales/{symbol}@1` を銘柄ごとに順次ポーリング
   - rss : Excelに `=RssTickList(...)` を書き込みスピル範囲を読む
2. 前回との差分（新規約定）だけを抽出（`TickDeduper`）
3. 当日ぶん・場中のみを対象にする
4. **売買方向はティックルールで推定**（約定値が直前より高い→buy / 低い→sell / **同値→flat**）
   ※歩み値には売買の別が無いための近似。
   **同値（ゼロティック）を独立扱いにしているのが重要**: 買い集めアルゴは同じ売り気配を
   叩き続けるため価格が動かないことが多く、「同値＝直前の方向を継承」とすると
   買いを売りと誤判定して**まったく検知できなくなる**（2026-07-31に修正）。
   既定の `buy_side_mode: non_down` では アップティック＋同値 を買い側として扱う
5. 「約定の丁度N秒後の買い」を当日カウントし、5回でWATCH・10回でSTRONG通知

**検知は場中（既定 09:00〜15:30）に限定**している。時間外はExcelを読みに行かず、
`idle_poll_seconds` ごとに時刻だけ確認して待機する。加えて次の2つを弾く:

- **時刻が場中の範囲外の約定**（寄り付き前の気配・引け後）
- **現在時刻より未来の約定**（＝前営業日の残りティック）

`RssTickList` は起動時点で前営業日の終盤ティック（例: 15:24）を返すため、これを弾かないと
寄り付き前や寄り直後に**前日ぶんを当日の検知として数えてしまう**（2026-08-07に修正）。

ログは `periodic_buy_rss/logs/periodic_buy_rss_YYYY-MM-DD.log` に日付別で保存。

## セットアップ

### 前提

**kabu（既定）の場合**: kabuステーションが起動・ログイン済みであること。それだけ。
統合ランナーと同じ接続を使うので追加の準備は不要。

**rss（旧方式）の場合のみ**、以下が必要:

1. **マーケットスピードII** を起動しログインしておく（RSSは起動中のみ更新される）
2. **Excel に「マーケットスピードII RSS」アドインを有効化**しておく
3. **空のExcelブックを1つ開いておく**（`TICKS` シートを作り数式を書き込む）

### 起動方法は2通り

**(A) 統合ランナーから自動起動（推奨）** — `runner/config.yaml` の
`periodic_buy_rss.enabled: true` により、以下だけで本ツールも一緒に起動する:

```powershell
cd strategies\runner\src
python main.py --config ../config.yaml
```

ログ・通知はランナー側（`runner/logs/`）に一元化される。
取得元が kabu ならランナーのkabuクライアントをそのまま使う。
rss の場合は Excel/MS2 が未起動でも再試行し、駄目なら警告のみでランナーは継続する。

**単体実行は rss のときだけ**。kabu を使う場合はランナー経由で起動すること
（kabuクライアントの受け渡しが必要なため）。

**(B) 単体で実行**

### インストールと実行

```powershell
cd strategies\periodic_buy_rss
pip install -r requirements.txt
# config.yaml は作成済み（config.example.yamlと同内容）。閾値や銘柄設定を変える場合は編集
cd src
python main.py --config ../config.yaml
```

停止は `Ctrl + C`。監視銘柄は既定で全ストラテジー共通の `strategies/symbols.yaml` を使う。

## 設定（config.yaml）

- `source`: 取得元（`"kabu"` 既定 / `"rss"`）
- `kabu.*`: kabu歩み値APIの設定（市場コード・1銘柄あたりの取得間隔）
- `rss.*`: Excel連携の設定（`source: "rss"` のときのみ使用）。
  ただし `session_start` / `session_end` / `idle_poll_seconds` は**両方式で共通**
- `debug_raw_batches`: 起動直後N回、読み取った歩み値の直近3件をログ出力（項目・時刻形式の確認用）
- `detector.*`: 検知条件。主要なものは以下

| キー | 既定 | 意味 |
|---|---|---|
| `delay_seconds` / `delay_tolerance_seconds` | 10.0 / **0.0** | 狙うラグと許容誤差。歩み値の時刻は秒未満切り捨てのため 0.0＝「表示上ちょうど10秒差」だけを数える（手集計と同じ基準）。取りこぼす場合は1.0に上げる |
| `trigger_side` | **`any`** | 起点約定の向き。「約定の10秒後の買い」を数えるため既定は不問。売り起点に絞るなら `sell`（同値(flat)も許容） |
| `buy_side_mode` | `non_down` | 買い側の判定。`non_down`=アップティック＋同値／`strict`=アップティックのみ／`any`=不問 |
| `lot_similarity_pct` | 0.0 | >0でロットの揃い方も要求（0.3→直近平均±30%以内） |
| `alert_tiers` | 5→WATCH, 10→STRONG | 当日の検知回数のしきい値 |

`rss.session_start` / `rss.session_end`（既定 09:00 / 15:30）で検知対象の時間帯を指定する。
時間外は `rss.idle_poll_seconds`（既定30秒）ごとに時刻確認だけ行い、Excelは読まない。

**`lot_similarity_pct` が誤検知を減らす最有力の条件**。買い集めアルゴは同じ株数
（例: 100株・200株）で刻むことが多いため、流動性の高い銘柄で「偶然10秒前にも約定があった」
だけのノイズを大きく削れる。まずは0（無効）で実データを見てから調整するとよい。

## ログの見方

```
[アルゴ買い集め(RSS)/WATCH] 4165 4165: 売り約定の約10.0秒後に買い上がる動きを本日5回検知
（歩み値ベース・現在値560円）。一定ラグで反応する買い集めアルゴの可能性（大量保有報告に向けた仕込みサインの疑い）
```

## 重要な前提・限界

- **売買の別は歩み値に含まれず、ティックルールで推定**している。気配（板）と突き合わせる方式より
  精度は落ちる。特に同値約定が続く場面では方向の取りこぼしがある
- **kabu**: レート制限（429）がある。当たった場合は空を返して次周回で取り直すため
  取りこぼしは起きないが、`kabu.poll_interval_seconds` を長くするのが望ましい。
  **毎回その日の全件が返る**ので、途中から起動しても当日ぶんを最初から数え直せる
- **rss**: 「直近最大300件」しか返らないため、**ポーリングが空きすぎると取りこぼす**。
  また起動時点で直近300件しか遡れないので、正確なカウントには寄り付き前からの起動が必要
- 歩み値の**時刻は秒未満が切り捨てられる**。既定の `delay_tolerance_seconds: 0.0` は
  「表示上ちょうど10秒差」だけを数える（手集計と同じ基準）。アルゴのラグが実際に揺れていて
  取りこぼす場合は 1.0 に上げる。初回は `debug_raw_batches` の出力で時刻形式・並び順を確認すること
- **WATCH(5回)はノイズが多い**。2026-08-06〜07の実データでは50銘柄中19銘柄で発火し、
  買いシグナルとしての期待値はマイナスだった（STRONG=10回のみプラス）。
  絞り込むには `alert_tiers` の下限引き上げか `lot_similarity_pct` の有効化を検討する
- rss は win32com を使うため **Windows + デスクトップExcel 専用**。kabu にはこの制約がない。
  検知ロジックは `tick_detector.py`（純Python）に分離してあり、どちらの取得元でも共通

## トラブルシューティング（rss=Excel経由のときのみ）

- **`呼び出し先が呼び出しを拒否しました` / `RPC_E_CALL_REJECTED (-2147418111)`**:
  Excelがビジー（セル編集中・ダイアログ表示中・RSS再計算中など）でCOM呼び出しを
  受け付けられない状態。本ツールは自動でリトライする（`com_retries`×`com_retry_delay`）。
  それでも出続ける場合は、Excelでセル編集を確定（Escや別セルクリック）し、開いている
  ダイアログを閉じてから再実行する。`config.yaml` の `rss.com_retries` を増やすのも有効
- **`起動中のExcelに接続できませんでした`**: Excelが起動していない。Excelを開いてから実行する
- 数式は書けたが値が空/エラー: マーケットスピードII本体が未起動・未ログイン、または
  RSSアドインが無効。`[DEBUG BATCH]` に何も出ない場合はまずこれを疑う

## 検知条件そのものの課題（未解決）

2026-08-10に kabu の歩み値で実データを調べたところ、**現在の判定条件では
流動性の高い銘柄でノイズだらけになる**ことが分かった。

| 銘柄 | 当日約定数 | ちょうど10秒差のペア |
|---|---|---|
| 4889 | 5,240件 | **3,388件** |
| 4013（勤次郎） | 192件 | 45件 |

約定間隔の分布を見ると 0〜11秒それぞれに約2万ペアあり、**10秒が特別ではない**。
「同ロットで10秒間隔が3回以上連続」まで絞ると 4889 で361連鎖、4013 では0連鎖。

ユーザーが目視で見つけた「規則的な買い集め」を機械的に再現するには、
ロットの一致・連続性・方向をどう組み合わせるかの検討が必要。
**kabuの歩み値APIで過去2営業日ぶんが取れるようになったため、
実データで条件を検証してから決められる**（RSSでは300件しか無く不可能だった）。
